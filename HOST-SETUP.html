Warum ZFS und nicht XFS

Im Plan standen beide Wege gleichberechtigt. Wenn du den Host ohnehin frisch aufsetzt, fällt die Entscheidung eindeutig auf ZFS — und der Grund sind nicht die Quotas, die können beide, sondern die Snapshots.

AufgabeXFS mit prjquotaZFS
Harte Speichergrenze pro Server Project-ID verwalten, in DB mitführen zfs set quota=10G …, sofort wirksam
Belegten Platz auslesen xfs_quota-Report parsen zfs list, exakt und ohne Verzeichnis-Scan
Backup erstellen tar über die ganze Welt, Minuten mit Schreibsperre Snapshot, ~1 Sekunde, danach läuft der Server weiter
Backup zurückspielen Verzeichnis leeren, entpacken, Minuten zfs rollback, Sekunden
Platzbedarf für 20 Backups 20 × volle Weltgröße nur die Deltas
Kompression keine lz4, Weltdaten schrumpfen typisch auf ein Drittel
RAM-Kosten keine ARC-Cache, muss gedeckelt werden

Der einzige echte Nachteil ist der ARC-Cache, der sich sonst nimmt, was er kriegt — und RAM ist bei uns die knappe Ressource, weil jede JVM ihren Heap tatsächlich belegt. Deshalb bekommt ARC in Schritt 4 eine harte Obergrenze und wird in node.reservedMemoryMb eingerechnet. Damit ist der Nachteil verwaltet, die Vorteile bleiben.

Snapshots im selben Pool sind kein Backup gegen Plattenausfall. Sie schützen gegen das, was tatsächlich täglich passiert: Griefing, ein kaputtes Plugin, ein versehentliches /kill @a. Stirbt die Platte, sind Pool und Snapshots gleichzeitig weg. Für Katastrophenschutz braucht es ein nächtliches zfs send auf ein anderes Gerät — bei einer einzelnen Platte im Rechner ist das die NAS.

Eine Platte reicht. ZFS will ein Blockgerät, keine ganze Platte — eine Partition tut es genauso. Der einzige Unterschied zum Zwei-Platten-Aufbau: Du musst bei der Ubuntu-Installation einmal von Hand partitionieren, statt den Installer die Systemplatte allein füllen zu lassen. Das ist Schritt 2.

Warum das System nicht einfach mit auf ZFS liegt. Der Installer bietet ZFS für die Wurzel an — dann bräuchte es keine Partitionierung, alles läge in einem Pool. Trotzdem nicht: Docker legt Images und Container-Schichten in /var/lib/docker ab, und auf ZFS wählt Docker seinen zfs-Treiber statt overlay2. Overlay2 auf ext4 ist der am besten getestete Pfad überhaupt und der, gegen den diese Anwendung entwickelt wurde. Dazu kämen Boot-Environments und ein GRUB, der ZFS lesen können muss. System einfach halten, ZFS genau dort einsetzen, wo es zählt: bei den Weltdaten.
Eine Platte heißt: ein einziger Ausfallpunkt. System, Welten und Snapshots liegen auf demselben Gerät. Snapshots schützen gegen Griefing, ein kaputtes Plugin, ein versehentliches /kill @a — gegen den Tod der SSD schützen sie nicht, sie sterben mit. Der einzige Schutz dagegen ist der nächtliche Strom auf die NAS. Richte ihn ein, bevor der erste fremde Nutzer einen Server bekommt, nicht danach.
02

Betriebssystem

Ubuntu Server 24.04 LTS. Ubuntu liefert ZFS als offiziell unterstütztes Paket mit, das erspart dir das DKMS-Gebastel, das man unter Debian betreibt. 24.04 ist bis 2029 versorgt und der ZFS-Stack darauf ist lange durchgeschüttelt. Ein neueres LTS geht auch, prüfe dann aber vor der Installation, ob zfsutils-linux für den mitgelieferten Kernel verfügbar ist — an dieser Kombination hängt alles Weitere.

Bei der Installation: minimale Serverinstallation, kein Desktop, SSH-Server aktivieren, deinen öffentlichen Schlüssel hinterlegen.

Die Platte aufteilen

Im Installer Custom storage layout wählen, nicht den geführten Weg. Drei Partitionen anlegen und den Rest frei lassen:

Kein separates /boot nötig, kein LVM, keine Verschlüsselung — GRUB liest ext4 direkt. 120 GB für das System sind reichlich: Ubuntu, die Docker-Images (Java-Varianten, Postgres, Redis, Caddy, mc-router — zusammen unter 10 GB), die Anwendung und die Logs. Der freie Bereich bleibt unangetastet, bis ihn Schritt 3 zum Pool macht.

Schon installiert und alles vergeben? Dann sieh zuerst nach, ob überhaupt etwas fehlt: Die geführte LVM-Installation von Ubuntu deckelt das Wurzel-Volume und lässt den Rest der Volume-Gruppe unbenutzt — sudo vgs zeigt es unter VFree. Ist dort Platz, brauchst du gar nichts zu tun; deploy/setup.sh findet ihn und bietet an, ein Volume daraus zu schneiden. Dasselbe gilt für unpartitionierten Platz, den sudo sgdisk -p /dev/nvme0n1 als Total free space ausweist. Erst wenn beides leer ausgeht, musst du wirklich verkleinern — bei LVM mit resize2fs und lvreduce, sonst mit gparted von einem Live-Stick. Neu installieren ist an dem Punkt oft der schnellere Weg.

03

ZFS-Pool anlegen

deploy/setup.sh erledigt diesen Schritt mit — inklusive Anlegen der Partition, wenn du den Rest der Platte frei gelassen hast. Was folgt, beschreibt, was dabei passiert, und ist der Weg für den Fall, dass du es von Hand tun willst.

Immer /dev/disk/by-id/ verwenden, nie /dev/nvme0n1p3. Kernel-Gerätenamen können sich zwischen Neustarts ändern, sobald eine Platte dazukommt. Ein Pool, der auf /dev/sdb2 zeigt, findet nach dem Einbau der Backup-Platte womöglich das falsche Gerät. Die IDs sind stabil. 
# Freien Platz und bestehende Partitionen ansehen
lsblk
sudo sgdisk -p /dev/nvme0n1        # Zeile "Total free space is …"

# Partition im größten freien Block anlegen. 0:0:0 heißt: nächste freie
# Nummer, Anfang und Ende des Blocks. Bestehende Partitionen kann das
# nicht berühren — deshalb ist dieser Befehl ungefährlich.
sudo sgdisk -n 0:0:0 -t 0:bf01 -c 0:mc-saas /dev/nvme0n1
sudo partprobe /dev/nvme0n1

# Stabile ID der neuen Partition heraussuchen (endet auf -partN)
ls -l /dev/disk/by-id/ | grep nvme0n1p

sudo zpool create -o ashift=12 \
  -O compression=lz4 \
  -O atime=off \
  -O xattr=sa \
  -O acltype=posixacl \
  -O canmount=off \
  -m none \
  tank /dev/disk/by-id/DEINE-ID-partN
Die Geräte-ID zweimal lesen. zpool create fragt nicht nach und überschreibt, was da ist. Auf derselben Platte liegt zu diesem Zeitpunkt dein frisch installiertes Ubuntu. Der Name muss auf -partN enden — ohne Partitionsnummer meinst du die ganze Platte, und dann ist das System weg. lsblk gegenprüfen: Die richtige Zeile hat rund 810 G und keinen Einhängepunkt.
OptionWofür
ashift=124-KB-Sektoren. Falsch gesetzt kostet es dauerhaft Leistung und ist nachträglich nicht änderbar.
compression=lz4Weltdaten schrumpfen typisch auf ein Drittel. Die CPU-Kosten sind vernachlässigbar, der gesparte I/O macht es netto schneller.
atime=offOhne das schreibt der Host bei jedem Lesezugriff einen Zeitstempel zurück. Bei Minecraft sind das sehr viele überflüssige Schreibvorgänge.
xattr=saErweiterte Attribute inline statt in Extra-Objekten — spürbar weniger I/O.
-m none, canmount=offDer Pool selbst wird nirgends eingehängt, nur seine Datasets. Hält / sauber.

Datasets

sudo zfs create -o mountpoint=/srv/mc      tank/mc
sudo zfs create -o mountpoint=/srv/backups tank/backups

# So wird der Agent später pro Server ein Dataset anlegen:
#   zfs create -o quota=10G tank/mc/srv-abc123

# Es mountet automatisch unter /srv/mc/srv-abc123 und wird dorthin gebind-mountet.

Die 1000:1000 sind kein Zufall: das itzg/minecraft-server-Image läuft als UID 1000. Gehört das Verzeichnis root, startet der Server nicht.

Backup-Ziel: die NAS

Eine dritte Platte gibt es nicht, also geht der Katastrophen-Backup auf die DXP4800. zfs send erzeugt einen Datenstrom, den man einfach als Datei ablegen kann — die NAS muss dafür kein ZFS können.

# NAS dauerhaft einhängen (Zugangsdaten in eine 0600-Datei, nicht in fstab)
sudo mkdir -p /mnt/nas
sudo apt install -y cifs-utils
# /etc/fstab:
#   //DXP4800/Backups /mnt/nas cifs credentials=/etc/nas.cred,uid=0,gid=0,_netdev 0 0

# Vollsicherung eines Servers als Datei
zfs send tank/mc/srv-abc123@2026-08-14 | zstd > /mnt/nas/srv-abc123-2026-08-14.zfs.zst

# Später inkrementell — überträgt nur die Differenz zum Vortag
zfs send -i @2026-08-13 tank/mc/srv-abc123@2026-08-14 | zstd > /mnt/nas/…

# Zurückholen
zstd -d < /mnt/nas/srv-abc123-2026-08-14.zfs.zst | zfs recv tank/mc/srv-abc123
Snapshots und NAS-Ströme sind zwei verschiedene Dinge. Die Snapshots im Pool bedienen den Backup-Knopf im Panel: schnell, häufig, für Griefing und kaputte Plugins. Die Ströme auf der NAS sind der Schutz gegen den Ausfall der SSD und laufen nächtlich als Cron. Nur Letztere überleben, wenn die Platte stirbt.
04

ARC begrenzen

Der wichtigste Schritt des ganzen Runbooks. Ohne Deckel wächst der ZFS-Cache, bis der Kernel Druck meldet — und dieser Druck trifft dann JVMs, die ihren Speicher nicht hergeben können. Das Ergebnis sind OOM-Kills mitten im Spielbetrieb.

# 48 GB RAM → 6 GB ARC (6 * 1024^3 = 6442450944)
echo "options zfs zfs_arc_max=6442450944" | sudo tee /etc/modprobe.d/zfs.conf
sudo update-initramfs -u

# Sofort wirksam ohne Neustart:
echo 6442450944 | sudo tee /sys/module/zfs/parameters/zfs_arc_max

# Kontrolle
grep -E '^(c_max|size)' /proc/spl/kstat/zfs/arcstats
Diese Zahl gehört ins Datenmodell. ARC plus OS plus Postgres/Redis/App/Agent wandern als node.reservedMemoryMb in die Node-Zeile. Die Kapazitätsprüfung beim Anlegen eines Servers zieht sie ab, damit sich das Panel nie mehr RAM verspricht, als tatsächlich da ist.

# Internes Netz für die Minecraft-Container
sudo docker network create mc-net

live-restore lohnt sich hier besonders: damit überleben laufende Container einen Neustart des Docker-Daemons. Ein Daemon-Update wirft dann nicht alle Spieler gleichzeitig raus.

06

Kernel-Parameter und Limits

sudo tee /etc/sysctl.d/99-mc.conf > /dev/null <<'EOF'
# JVMs dürfen niemals swappen — lieber sauber sterben als das System lahmlegen
vm.swappiness = 1

# Die JVM legt sehr viele Speicher-Mappings an
vm.max_map_count = 262144

# Viele gleichzeitige Verbindungen über den Router
net.core.somaxconn = 1024
net.ipv4.tcp_max_syn_backlog = 2048

fs.file-max = 1000000
fs.inotify.max_user_watches = 524288
EOF

sudo sysctl --system

Swap komplett abzuschalten ist reizvoll, aber riskant: ohne jeden Puffer trifft der OOM-Killer im Zweifel Postgres statt einen Spielserver. Besser ist ein kleiner Swap (8 GB) zusammen mit swappiness=1 — dann wird er praktisch nie benutzt, fängt aber Spitzen ab.

Zeit synchron halten (systemd-timesyncd ist bei Ubuntu aktiv, kurz mit timedatectl prüfen). Schiefe Uhren äußern sich später als unerklärliche TLS-Fehler und unlesbare Logs.

07

Firewall und SSH

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 25565/tcp
sudo ufw enable
Docker umgeht ufw. Veröffentlicht ein Container einen Port, schreibt Docker eigene iptables-Regeln, die an ufw vorbeigehen — der Port ist dann offen, obwohl ufw ihn verbietet. Unser Aufbau umgeht das Problem, weil außer mc-router kein Container Ports veröffentlicht. Halte das durch: keine ports:-Einträge bei Minecraft-Containern, bei Postgres, bei Redis, beim Agent. Kontrolliere es nach jedem Compose-Umbau mit docker ps --format '{{.Names}} {{.Ports}}'.

Weiterleitung im Heimrouter

Die Firewall auf dem Host ist die eine Hälfte, der Router davor die andere. Genau drei Ports gehören aus dem Internet auf den Host — mehr nicht.

PortProtokollWofürPflicht
25565TCPMinecraft, sämtliche Server über mc-routerja
443TCPPanel unter panel.neuhauser.appja
80TCPWeiterleitung auf HTTPS und ACME-Prüfungempfohlen
Niemals weiterleiten: 22, 5432, 6379, 8787, 8080, 25575. Diese Dienste sind bewusst an 127.0.0.1 gebunden. Besonders 8787: Der Agent hält den Docker-Socket, eine offene Weiterleitung dorthin gäbe jedem im Internet Root auf dem Host. Kontrolle mit docker ps --format '{{.Names}} {{.Ports}}' — außer bei mc-router darf dort nirgends 0.0.0.0 stehen.

Port 80 ist nicht zwingend: Caddy holt das Zertifikat notfalls allein über 443 (TLS-ALPN-01). Ohne 80 landen aber alle, die http:// eintippen, im Leeren statt auf HTTPS.

Drei Voraussetzungen davor

  • Feste interne Adresse für den Host, per DHCP-Reservierung. Sonst zeigt die Weiterleitung nach dem nächsten Neustart auf ein anderes Gerät im Netz.
  • DynDNS, falls die öffentliche IP wechselt — bei Privatanschlüssen die Regel. Router können das meist nur für einen einzelnen Hostnamen; für *.mc.neuhauser.app braucht es in der Regel einen Updater auf dem Host, der die API des DNS-Anbieters bedient.
  • Eine echte öffentliche IPv4. Bei DS-Lite (verbreitet bei Kabelanschlüssen) teilen sich viele Kunden eine Adresse, und Portweiterleitung funktioniert für IPv4 gar nicht. Erkennbar an einer WAN-Adresse aus 100.64.0.0/10 oder daran, dass im Router überhaupt keine IPv4 auftaucht. Dann bleiben IPv6-only mit AAAA-Records oder ein Tunnel über einen kleinen VPS.

SSH und Grundhärtung

# SSH: nur Schlüssel, kein Root-Login mit Passwort
sudo sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/^#*PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
sudo systemctl restart ssh

sudo apt install -y fail2ban unattended-upgrades

Bei den automatischen Updates nur Sicherheitsaktualisierungen zulassen und Kernel-Upgrades im Blick behalten: Ein neuer Kernel ohne passendes ZFS-Modul bedeutet, dass der Pool nach dem Neustart nicht da ist. Deshalb nach jedem Kernel-Update ein kontrollierter Reboot mit anschließendem zpool status, nicht blind automatisch neu starten lassen.

08

Vorbereitung für den Agent

Hier eine Präzisierung gegenüber dem Bauplan, die sich aus der ZFS-Entscheidung ergibt: der Agent läuft nicht als Container, sondern als systemd-Dienst direkt auf dem Host.

Der Grund ist praktisch. Der Agent muss zfs create, zfs set quota, zfs snapshot und zfs rollback ausführen. Aus einem Container heraus ginge das nur mit --privileged und durchgereichtem /dev/zfs — also mit deutlich mehr Rechten als jetzt. Und ein Sicherheitsverlust ist es nicht: Wer den Docker-Socket hat, ist auf dem Host ohnehin root-gleichwertig. Der Agent auf dem Host macht diese Tatsache nur sichtbar, statt sie hinter einer Container-Grenze zu verstecken, die keine ist.

Nebenbei wird dadurch einiges einfacher: Dateimanager-Zugriffe gehen direkt aufs Dateisystem statt durch einen Mount, und Log-Streams brauchen keinen zusätzlichen Hop.

# Dienstkonto (in der Docker-Gruppe, aber ohne Login-Shell)
sudo useradd --system --home /opt/mc-agent --shell /usr/sbin/nologin mcagent
sudo usermod -aG docker mcagent
sudo mkdir -p /opt/mc-agent /etc/mc-agent
sudo chown mcagent:mcagent /opt/mc-agent

# ZFS-Rechte gezielt delegieren statt pauschal sudo zu geben
sudo zfs allow -u mcagent create,destroy,mount,quota,snapshot,rollback,hold tank/mc
sudo zfs allow -u mcagent create,destroy,mount,snapshot,receive tank/backups

# Der Agent hört nur lokal — nie auf 0.0.0.0
#   MC_AGENT_BIND=127.0.0.1:8787
#   MC_AGENT_TOKEN=  → gehört in node.agentToken
sudo touch /etc/mc-agent/env
sudo chmod 600 /etc/mc-agent/env
zfs allow statt sudo. Die Delegation gibt dem Dienstkonto genau die Operationen, und nur unterhalb von tank/mc und tank/backups. Ein Fehler im Agent kann damit nicht den Systempool anfassen. Für mount braucht ZFS unter Linux je nach Version zusätzlich CAP_SYS_ADMIN — falls das Anlegen scheitert, in der systemd-Unit AmbientCapabilities=CAP_SYS_ADMIN ergänzen, bevor du zu pauschalem sudo greifst.

Damit die App im Container den Agent auf dem Host erreicht, hängt sie an extra_hosts: ["host.docker.internal:host-gateway"] und spricht http://host.docker.internal:8787 an. Der Port bleibt an 127.0.0.1 gebunden und ist von außen nicht sichtbar.

Praxistest: ein Server von Hand

Bevor eine Zeile Anwendungscode entsteht, einmal beweisen, dass die Kette trägt.

sudo chown 1000:1000 /srv/mc/probe

docker run -d --name mc-probe \
  --network mc-net \
  -v /srv/mc/probe:/data \
  --memory 2g --memory-swap 2g --cpus 2 --pids-limit 512 \
  --security-opt no-new-privileges:true \
  --stop-timeout 120 \
  -e EULA=TRUE -e TYPE=PAPER -e VERSION=1.21.8 \
  -e MAX_MEMORY=1536M \
  itzg/minecraft-server:java21

docker logs -f mc-probe    # auf: Done (…s)! For help, type "help"
zfs list tank/mc/probe     # zeigt gewachsenen Platz und die 1G-Quota

Beachte das Verhältnis: 2 GB Container-Limit, aber nur 1536 MB Heap. Genau die Lücke verhindert später die OOM-Kills. Danach aufräumen:

docker rm -f mc-probe
sudo zfs destroy tank/mc/probe

Was ich danach von dir brauche

Hardware und Domain stehen inzwischen fest, die Werte sind oben und im Repo eingetragen. Offen ist nur noch das DNS und der Mailversand.

.app erzwingt HTTPS. Die Domain steht auf der HSTS-Preload-Liste, die in jedem Browser fest eingebaut ist. Über http:// ist das Panel damit grundsätzlich nicht erreichbar — auch nicht testweise, auch nicht mit Zertifikatswarnung. Für Minecraft selbst spielt HSTS keine Rolle — das ist kein HTTP. Der Wildcard-Eintrag genügt, ein SRV-Record ist nicht nötig, solange die Server auf dem Standardport 25565 laufen.
